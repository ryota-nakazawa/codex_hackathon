## フェーズ2: 解決手段の選定

### このフェーズでやったこと

- `GPTs`、`エージェント`、`軽量アプリ` の候補比較を行った。
- PoC として最小実現手段は `軽量 web アプリ` と判断した。
- 理由は、画像アップロード、患者 ID 管理、出力セクション分離、画面導線の固定化が必要であり、GPTs 単体では運用導線を十分に固定しづらいため。
- エージェントは将来の自動連携には有効だが、当時の PoC スコープには重いと判断した。

### 選定理由とトレードオフ

- 採用
  - 軽量 web アプリ
- 理由
  - 画像入力、テキスト入力、患者単位の表示、出力レイアウトの固定に向いている
  - 半自動運用でも価値検証しやすい
- トレードオフ
  - GPTs より実装コストは高い
  - エージェントほどの自動化拡張性は最初からは持たない

### このフェーズで使ったエージェント

- 設計エージェント
  - 候補比較の整理
  - 画面責務と API 責務の切り分け案の提示
- メインエージェント
  - 最終方針の採用判断

## フェーズ4: 入出力整理

### このフェーズでやったこと

- 初期 PoC の入力を `カルテ要点メモ`、`レントゲン画像`、`患者要望` を中心に整理した。
- 出力を `要約`、`要確認ポイント`、`患者説明文案`、`参考観点` に分けた。
- その後、予約導線の追加に合わせて、予約フォーム入力、予約一覧表示、患者詳細表示、過去履歴、レントゲン解析結果という単位へ拡張した。
- 患者詳細では `xrayStudies`、`reports`、`history` を画面表示単位として整理した。

### データの流れ

- 患者サイト
  - 患者が予約フォームを送信
  - 予約データと患者データを生成
- 管理画面
  - 予約一覧から患者を選択
  - 患者詳細で過去履歴、レポート、レントゲン情報を確認
- AI 解析
  - レントゲン画像をアップロード
  - `/api/patients/:id/xrays/analyze` で解析
  - 結果を `xrayStudies`、`reports`、`history` に反映

### 未確定から絞り込んだ点

- `テキストのみ入力` の場合は画像由来の断定を避ける
- `画像のみ入力` の場合は背景事情の断定を避ける
- `mock`、`live`、`fallback` の 3 経路を維持する

### このフェーズで使ったエージェント

- バックエンド実装エージェント
  - API 入出力設計
  - 患者詳細向けのデータ構造整理
- ダミーデータ準備エージェント
  - `data/*.json` の患者、予約、詳細、サイトデータ作成
- メインエージェント
  - UI 表示単位への変換
